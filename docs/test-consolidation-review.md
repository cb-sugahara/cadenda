# テスト統合案レビューと推奨方針

2026-11-13 / 対象: `_review/test_consolidation_plan.md`

**整理・統合には賛成するが、提示された削除計画はそのまま採用しない。** 目標は変更に必要な確認を短く分かりやすくすること。75件・6ファイル・1秒未満という数値を先に決めて検証を削らない。

本書はレビュー結果であり、テストの削除・移動・実行設定の変更はまだ行っていない。

## 前提の修正

- GUIは手動コード検索をなくしたが、単回ticket・Cookieセッション・有効期限・Host/Origin/CSRF保護を使っている。認証は撤廃していない。
- launch_gateは現役で、PGIDを永続化する前に子が動かないことを保証する。廃止予定ではない。
- Outboxは現役で、通知対象の2種類への限定は未実装。通知を絞っても、送信後クラッシュ・重複照合・短いSQLトランザクションの確認は必要。
- stagingは通常画面とv0経路から除外したが、明示CLI/APIと実装は残っている。「経路から除外」と「製品から削除」を区別する。
- バックアップは現行もSQLiteの標準backup APIとGit bundle、BeadsのDoltネイティブ保存を利用する。同一repo内のタグでは置き換えない。

## 採用する整理、採用しない削除

| 提案 | 判断 |
|---|---|
| worker / pipeline / launch_gateの集約 | 採用可能。実行系のファイルへ移してよいが、最初はassertとケースを維持した移動だけにする |
| adaptersの共通fixture整理 | 採用可能。呼出し準備の重複を減らす。Codexの不正応答・権限境界とfmの拒否条件は保持 |
| stagingテスト全削除 | 不採用。任意機能のセットへ分類できるが、入口が残る限り全体回帰には残す |
| 認証テスト約18件の削除 | 不採用。現在も動く単回接続・期限・再起動結合・Cookie/CSRFの回帰を失う |
| launch_gateの1件削除 | 不採用。親停止時に子が勝手に動かないことはローカルでも必要。移動は可 |
| Outbox / 復旧テストの一括削除 | 不採用。現行動作を保護する。lease期限だけで再起動しないテストも含まれている |
| operationsを正常系4件へ圧縮 | 不採用。保存先逸脱・稼働中backup拒否・再起動上限・リセット競合は別の失敗条件 |
| パラメータ化ケースの代表例化 | 同じ故障を同じ経路で検出していると説明できる場合のみ。件数合わせでfor文にまとめない |
| テストコード比率・ファイル数の削減目標 | 不採用。比率だけでは過剰と判断しない。探しやすさと失敗時の診断しやすさを評価する |

## 推奨する進め方

1. **最初は分類と実行単位の整理。** 「v0コア」「任意機能」「実機結合」を区別する。実機結合は既存のintegration指定を再利用し、通常の編集確認から分離する。新しいテスト基盤は作らない。
2. **日常は変更に関係する試験を先に実行。** 例えば今回のTOP修正は`tests/test_boundaries.py`と`tests/test_server.py`、`node web/tests/api-response.test.mjs`が最初の確認になる。実行制御に触れたら実プロセス試験も省略しない。
3. **全体回帰は反映前や共有基盤変更時に実行。** 任意機能を含むPython試験と必要なNode/ブラウザ試験を残す。fm・staging自体や、共有するRecorder・認証・プロセス処理を変えた場合も任意機能の試験を実行する。
4. **必要なファイルだけ統合。** worker / pipeline / gateの移動を単独差分で行い、同時に削除や本体リファクタリングをしない。ファイル6個への集約を目的にしない。
5. **削除は最後に1件ずつ判断。** 削除元の故障条件、それを代わりに検出する残存テスト、検証対象の入口が本当に消えたかを示せる場合だけ行う。DBやworktree状態の使い回しで見かけ上速くしない。

この分類・統合自体もv0の実利用を止める必須工程にはしない。まず今ある試験の選び方を明確にし、コードを触るときに重複した準備処理だけを整理する。

## 常に維持する検証

- Origin / Host / CSRF、単回ticket、期限、server instance結合、変更操作の拒否。
- 候補write-tree、テスト後の変更検知、検証commitとの一致、独立レビューと人間確認の区別。
- PGID停止、PID登録前の親停止、ホスト内単一Run、古いPIDや期限を根拠に自動再実行しないこと。
- 現在の要件と成果物に結合した承認、古い依頼の拒否、正式判断receiptの保存。
- 秘密情報の除外、環境許可リスト、10MiB上限、先頭/末尾ログ、不正UTF-8でも成果物を閲覧できること。
- 実際のBeads応答形式の契約。今回のTOP障害のように、一覧のfull edgeと詳細のbrief linkを両方確認する。mockの正常形式1種類への圧縮はしない。
- 保持している任意機能の許可なし実行拒否と、外部送信・PCCへの自動代替禁止。

「ケース数は減ったが、また同じTOP障害を見逃す」整理は避ける。**検出する失敗の種類を維持しながら、準備コードと普段実行する範囲を小さくする**方針とする。
